Sync Bazel modules from a source registry to a destination according to workflow configuration.

## Synopsis

```bash
bz mod sync [workflow-name] [flags]
```

## Description

The `sync` command reads workflow definitions from a Starlark configuration file and syncs modules from the origin registry to the destination. It supports multiple destination types including local filesystems, HTTP servers, and git repositories.

The workflow name can be given with `--workflow`/`-w` or as a positional argument (`bz mod sync mirror`). If both are given they must match.

## Flags

| Flag | Short | Description |
|------|-------|-------------|
| `--workflow` | `-w` | Workflow name to execute (required unless `--list` or given positionally) |
| `--config` | `-c` | Config file path (default: `bz.star`) |
| `--dry-run` | `-n` | Show what would be synced without writing |
| `--list` | `-l` | List available workflows |
| `--modules` | `-m` | Override workflow modules (comma-separated) |
| `--verbose` | `-v` | Enable verbose output |

## Examples

### List Workflows

```bash
bz mod sync --list
```

Output:
```
Available workflows:
  dev         - Sync to local development
  staging     - Sync to staging server
  production  - Sync to production registry
```

### Run a Workflow

```bash
bz mod sync --workflow dev
```

Output:
```
Sync complete:
  Modules processed: 2
  Modules written:   3
  Modules skipped:   0
```

"Modules written" counts module versions written to the destination.

### Dry Run

Preview what would be synced without writing:

```bash
bz mod sync --workflow production --dry-run   # or: -n
```

A dry run counts what would be written and writes nothing. It does not fetch module files, so failures that only occur while fetching are not detected.

<Aside type="tip">
Always use `--dry-run` first when syncing to production to verify what will be changed.
</Aside>

### Custom Config File

```bash
bz mod sync --workflow dev --config /path/to/custom.star
```

### Override Modules

Sync only specific modules, ignoring the workflow's module list:

```bash
bz mod sync --workflow dev --modules rules_go,gazelle   # or: -m
```

### Verbose Output

```bash
bz mod sync --workflow dev --verbose
```

Verbose mode logs each version that is synced or skipped as it is processed.

## Configuration

The sync command reads from a Starlark configuration file. See [Configuration](/bz/configuration/) for details.

### Example Config

```starlark
# bz.star
bcr = registry.http("https://bcr.bazel.build")
mirror = registry.file("./bazel-registry")

sync.workflow(
    name = "dev",
    origin = bcr,
    destination = mirror,
    modules = ["rules_go", "rules_python"],
    versions = sync.latest(count = 2),
    transforms = [
        sync.skip_yanked(),
    ],
)
```

`transformations` is accepted as an alias of `transforms`; passing both is an error. `versions = sync.since(...)` is not supported yet because release dates are not available from the registry; the configuration loads and `--list` works, but running that workflow fails with an explicit error.

## Exit Codes

| Code | Description |
|------|-------------|
| 0 | Success (all modules synced, or skipped because they already exist) |
| 1 | Any failure: a configuration or usage error, or at least one module or version failed to sync |

When modules fail, the command still processes the remaining modules, then prints a `Failures:` summary listing each failing module (and version, when known) with its error, and exits with code 1.
