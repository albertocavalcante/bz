bz provides several security-focused features to help you manage supply chain risks in your Bazel projects.

## Overview

| Feature | Command | Description |
|---------|---------|-------------|
| Vulnerability Scanning | `bz audit` | Check dependencies against OSV database |
| License Compliance | `bz mod licenses` | Audit and enforce license policies |
| SBOM Generation | `bz sbom` | Generate software bills of materials |

## Vulnerability Scanning

The `bz audit` command scans your dependencies for known security vulnerabilities using the [Open Source Vulnerabilities (OSV)](https://osv.dev/) database.

### Basic Usage

```bash
# Scan all dependencies in MODULE.bazel
bz audit

# Output as JSON (for CI/CD integration)
bz audit --json

# Filter by severity
bz audit --severity=high       # Only high and critical
bz audit --severity=critical   # Only critical
```

### Coverage

<Aside type="caution">
OSV files its records under upstream package names (for example the Go module `github.com/bazelbuild/rules_go`), not under Bazel module names, and bz does not know which upstream package a module corresponds to. Today **no module can be checked**, so `bz audit` fails unless you pass `--allow-unchecked`, which makes it pass while auditing nothing. A module that is not checked is different from "no known vulnerabilities". Only the direct dependencies in `MODULE.bazel` are audited; transitive dependencies are not audited (unlike `bz sbom`, which includes them).
</Aside>

Every run states how many of your direct dependencies were actually checked, and lists each one that was not, with the reason. The output below is a real run in a project with `rules_go`, `rules_python` and `gazelle`:

```
Checked 0 of 3 direct dependencies.
Not checked (3): no package mapping: bz does not know which upstream package this module corresponds to
  - rules_go@0.50.1
  - rules_python@0.34.0
  - gazelle@0.38.0
help: vulnerability matching for Bazel modules is not available yet; --allow-unchecked accepts that and audits nothing
No direct dependency could be checked; no vulnerability data was obtained.
Error: 3 of 3 direct dependencies were not checked (use --allow-unchecked to accept this)
```

A dependency is also reported as not checked when its OSV query fails (`query failed: ...`). A finding whose severity could not be determined is shown as `UNKNOWN` and is never hidden by `--severity`.

### Show Fix Suggestions

```bash
bz audit --fix
```

Output:
```
Module      Version  ID              Severity  Summary           Fixed In
------      -------  --              --------  -------           --------
protobuf    25.3     GHSA-8r3f-844c  HIGH      Buffer overflow   25.4

Suggested fixes:
  bz mod update protobuf --version=25.4
```

### Ecosystem Mapping

<Aside type="note">
There is no automatic mapping from Bazel modules to OSV packages. An earlier version queried `rules_go` as a Go package and `rules_python` as a PyPI package: those names are not upstream package names, so the queries could not match, yet the modules were reported as checked.
</Aside>

`--ecosystem` queries one OSV ecosystem for every module, using the Bazel module name as the package name. The name must be one of [OSV's ecosystems](https://ossf.github.io/osv-schema/#affectedpackage-field) as bz knew them on 2026-11-24; case is normalised (`go` becomes `Go`), and a near miss is rejected with a suggestion. If OSV has added an ecosystem since, pass `--ecosystem-unverified` to send the name as given; bz warns on stderr, because a misspelling would silently match nothing.

```bash
bz audit --ecosystem=Go
```

```
Queried 3 of 3 direct dependencies as Go packages named after the module.
No OSV records found under these names in Go; this does not show the modules are free of vulnerabilities.
```

stderr: `note: --ecosystem=Go queries module names as package names; exit status 0 does not mean the modules were audited`.

This only finds records for modules whose name equals the upstream package name, so bz says "queried", never "checked", and never reports a clean result. If a query fails, bz says so and does not claim that no records were found for that module. Exit status is 0 when no records come back (with the note above) and 1 when records are found. Do not use `--ecosystem` to make a CI job pass: that exit status 0 audits nothing for the modules whose names are not upstream package names.

### Exit Codes

| Situation | Exit code |
|-----------|-----------|
| `--ecosystem` given, no records at or above `--severity` (a note is printed on stderr) | 0 |
| Vulnerabilities found | 1 |
| Any OSV query failed | 1 (also with `--allow-unchecked`) |
| Any direct dependency not checked (no package mapping) | 1, unless `--allow-unchecked` |
| Invalid `--severity` or `--ecosystem` value | 1 |

`--allow-unchecked` keeps a job passing while auditing nothing. It accepts dependencies that have no package mapping: they are still listed, but do not fail the run. A failed lookup is never accepted. A project that passes only with `--allow-unchecked` has not been audited for those dependencies: read the `Checked N of M direct dependencies` line, or the `summary` object in the JSON output.

### CI/CD Integration

The job fails whenever vulnerabilities are found, a query fails, or a direct dependency could not be checked:

```yaml
# GitHub Actions example
jobs:
  security:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Install bz
        run: go install github.com/albertocavalcante/bz@latest
      - name: Security audit
        run: bz audit --severity=high
```

Adding `--allow-unchecked` lets the job pass while some dependencies remain unchecked. Use it only when you accept that those dependencies are not audited.

```yaml
# GitLab CI example
security_scan:
  script:
    - bz audit --json > audit-report.json
  artifacts:
    reports:
      security: audit-report.json
  allow_failure: false
```

### JSON Output Schema

From the same project (`bz audit --json`):

```json
{
  "total": 3,
  "vulnerable": 0,
  "vulnerabilities": [],
  "summary": { "scope": "direct", "total": 3, "checked": 0, "unchecked": 3, "failed": 0 },
  "unchecked": [
    { "module": "rules_go", "version": "0.50.1", "reason": "no package mapping: bz does not know which upstream package this module corresponds to" },
    { "module": "rules_python", "version": "0.34.0", "reason": "no package mapping: bz does not know which upstream package this module corresponds to" },
    { "module": "gazelle", "version": "0.38.0", "reason": "no package mapping: bz does not know which upstream package this module corresponds to" }
  ]
}
```

With `--ecosystem`, `summary.ecosystem` holds the forced ecosystem.

`summary.scope` is always `direct`: only direct dependencies are counted and audited. `summary.unchecked` counts every dependency without vulnerability data, including the `summary.failed` ones whose query failed. The `unchecked` array lists them with the reason. After the project has been loaded, JSON is written to stdout on every path, including failures; the exit status carries the verdict.

## License Compliance

The `bz mod licenses` command helps you understand and enforce license policies for your dependencies.

### List All Licenses

```bash
bz mod licenses
```

Output:
```
Module          Version  License
------          -------  -------
bazel_skylib    1.5.0    Apache-2.0
rules_go        0.50.1   Apache-2.0
rules_python    0.35.0   Apache-2.0
protobuf        25.4     BSD-3-Clause

Summary: 3 Apache-2.0, 1 BSD-3-Clause
```

### License Summary

```bash
bz mod licenses --summary
```

Output:
```
License       Count
-------       -----
Apache-2.0    3
BSD-3-Clause  1
```

### Policy Enforcement

Enforce license policies using `--check` with `--allow` or `--deny`:

<Tabs>
<TabItem label="Deny List">
```bash
# Fail if any copyleft licenses are found
bz mod licenses --check --deny=GPL-2.0,GPL-3.0,LGPL-2.1,LGPL-3.0
```

If a denied license is found:
```
license policy violation:
  - protobuf@25.3: GPL-3.0
```
Exit code: 1
</TabItem>
<TabItem label="Allow List">
```bash
# Only allow specific permissive licenses
bz mod licenses --check --allow=MIT,Apache-2.0,BSD-2-Clause,BSD-3-Clause
```

If an unlisted license is found:
```
license policy violation:
  - custom_module@1.0.0: Proprietary
```
Exit code: 1
</TabItem>
</Tabs>

### CI/CD Integration

```yaml
# GitHub Actions
- name: License check
  run: bz mod licenses --check --deny=GPL-2.0,GPL-3.0,LGPL-3.0
```

### Common License Identifiers

| License | SPDX Identifier |
|---------|-----------------|
| Apache License 2.0 | `Apache-2.0` |
| MIT License | `MIT` |
| BSD 2-Clause | `BSD-2-Clause` |
| BSD 3-Clause | `BSD-3-Clause` |
| GNU GPL v2 | `GPL-2.0` |
| GNU GPL v3 | `GPL-3.0` |
| GNU LGPL v3 | `LGPL-3.0` |
| Mozilla Public License 2.0 | `MPL-2.0` |

<Aside type="tip">
License information comes from the registry's `source.json` files. If a module shows "Unknown", the registry may not have license metadata for that version.
</Aside>

## SBOM Generation

Generate Software Bills of Materials (SBOMs) in industry-standard formats for compliance and supply chain transparency.

### Supported Formats

| Format | Standard | Use Case |
|--------|----------|----------|
| SPDX 2.3 | ISO/IEC 5962:2021 | Compliance, legal review |
| CycloneDX 1.4 | OWASP | Security tools, vulnerability management |

### Generate SPDX SBOM

```bash
# Output to stdout
bz sbom

# Write to file
bz sbom --output=sbom.spdx.json
```

Example SPDX output (truncated):
```json
{
  "spdxVersion": "SPDX-2.3",
  "dataLicense": "CC0-1.0",
  "SPDXID": "SPDXRef-DOCUMENT",
  "name": "my_project",
  "documentNamespace": "https://spdx.org/spdxdocs/my_project-0.1.0-...",
  "packages": [
    {
      "SPDXID": "SPDXRef-Package-rules-go-0.50.1",
      "name": "rules_go",
      "versionInfo": "0.50.1",
      "downloadLocation": "https://bcr.bazel.build/modules/rules_go/0.50.1/source.tar.gz",
      "externalRefs": [
        {
          "referenceCategory": "PACKAGE-MANAGER",
          "referenceType": "purl",
          "referenceLocator": "pkg:bazel/rules_go@0.50.1"
        }
      ]
    }
  ]
}
```

### Generate CycloneDX SBOM

```bash
bz sbom --format=cyclonedx --output=sbom.cdx.json
```

Example CycloneDX output (truncated):
```json
{
  "bomFormat": "CycloneDX",
  "specVersion": "1.4",
  "version": 1,
  "metadata": {
    "timestamp": "2024-01-15T10:30:00Z",
    "component": {
      "type": "application",
      "name": "my_project",
      "version": "0.1.0"
    }
  },
  "components": [
    {
      "type": "library",
      "name": "rules_go",
      "version": "0.50.1",
      "purl": "pkg:bazel/rules_go@0.50.1"
    }
  ]
}
```

### Include/Exclude Transitive Dependencies

```bash
# Include all transitive dependencies (default)
bz sbom --include-transitive=true

# Direct dependencies only
bz sbom --include-transitive=false
```

### CI/CD Integration

```yaml
# Generate SBOM on release
jobs:
  release:
    steps:
      - name: Generate SBOM
        run: |
          bz sbom --format=spdx --output=sbom.spdx.json
          bz sbom --format=cyclonedx --output=sbom.cdx.json
      - name: Upload SBOM
        uses: actions/upload-artifact@v4
        with:
          name: sbom
          path: |
            sbom.spdx.json
            sbom.cdx.json
```

## Complete Security Pipeline

Here's a complete security workflow combining all features:

```yaml
# .github/workflows/security.yml
name: Security Checks

on:
  push:
    branches: [main]
  pull_request:
  schedule:
    - cron: '0 0 * * *'  # Daily at midnight

jobs:
  security:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Setup Go
        uses: actions/setup-go@v5
        with:
          go-version: '1.25'

      - name: Install bz
        run: go install github.com/albertocavalcante/bz@latest

      - name: Vulnerability scan
        run: bz audit --json > audit-report.json

      - name: License compliance
        if: ${{ !cancelled() }}
        run: bz mod licenses --check --deny=GPL-2.0,GPL-3.0,LGPL-3.0

      - name: Generate SBOM
        if: ${{ !cancelled() }}
        run: |
          bz sbom --format=spdx --output=sbom.spdx.json
          bz sbom --format=cyclonedx --output=sbom.cdx.json

      - name: Upload security artifacts
        if: ${{ !cancelled() }}
        uses: actions/upload-artifact@v4
        with:
          name: security-reports
          path: |
            audit-report.json
            sbom.spdx.json
            sbom.cdx.json
```

## Best Practices

### Regular Scanning

- Run `bz audit` daily or on every PR
- Set severity thresholds appropriate to your risk tolerance
- Review and update dependencies regularly with `bz mod outdated` and `bz mod update`

### License Governance

- Define an organizational license policy (allow list or deny list)
- Enforce policy in CI/CD pipelines
- Review "Unknown" licenses manually

### SBOM Management

- Generate SBOMs for every release
- Store SBOMs alongside release artifacts
- Use both SPDX and CycloneDX for maximum tool compatibility

### Supply Chain Security

- Pin dependency versions explicitly (avoid floating versions)
- Use `bz cache verify` to ensure reproducible builds
- Consider air-gapped setups for sensitive environments
